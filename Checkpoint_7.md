# Итоговый вывод

Проверялась двухэтапная модель:

1. Candidate generation — отбор кандидатов.
2. Reranking — сортировка кандидатов.

Выбрано 18 пользователей из test. В train этих пользователей нет.

## 1. Candidate generation

Тестировались поломки:

* удаление верхних кандидатов;
* отбор хвостовых кандидатов;
* случайный отбор;
* смещение в популярные треки.

Худший сценарий: only_tail50.

Результат:

* overlap top-10 = 0.21;
* изменилось 6.72 айтема из 10;
* top10_rel снизился на 1.61.

Вывод: если релевантный трек не попал в candidate pool, reranker его не восстановит.

## 2. Reranking

Candidate pool фиксированный. Ломались только признаки.

Худший сценарий: поломка user-item признаков.

Результат:

* overlap top-10 = 0.25;
* изменилось 6.33 айтема из 10;
* top10_rel снизился на 1.11.

Вывод: reranker сильнее всего зависит от признаков связи пользователь-трек.

## 3. Отдельные признаки

Самая чувствительная фича: ui_n_events.

Результат:

* overlap top-10 = 0.49;
* изменилось 3.77 айтема из 10.

В худшем кейсе days_before_test снизил top10_rel у пользователя 358600 с 6 до 2.

Вывод: основные риски — user-item фичи:

* ui_n_events;
* days_before_test;
* mean_played_ratio;
* interaction_weight.

## Общий вывод

Candidate generation влияет на состав candidate pool. Ошибка на этом этапе необратима для reranker.

Reranking влияет на порядок внутри candidate pool. Самая опасная поломка — отсутствие или искажение user-item признаков.

Для мониторинга нужно контролировать:

* состав candidate pool;
* долю релевантных кандидатов;
* наличие user-item признаков;
* стабильность top-10.
